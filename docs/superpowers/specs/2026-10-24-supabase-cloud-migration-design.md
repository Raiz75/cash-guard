# Cash Guard: Supabase Cloud Migration — Design

**Date:** 2026-10-24
**Status:** Approved
**Breaking change:** Yes (target version 2.0.0)

## Goal

Replace the browser-only Dexie/IndexedDB database with a Supabase Postgres database so a user's finances live in the cloud, are tied to an account, and are reachable from any device.

## Non-goals

- Offline data access. The app is online-only after this change.
- Migrating existing IndexedDB data. The project is pre-release and starts fresh.
- Realtime multi-device push. Data refreshes on open, focus, reconnect, and after writes.
- Social login, MFA, password reset, or account management screens. Email + password only.

## Decisions

| Decision | Choice | Rationale |
| --- | --- | --- |
| Data ownership | Per-user rows protected by Row Level Security | The publishable key is public; RLS is the security boundary |
| Auth | Supabase Auth email + password | Simple, supports multiple devices, no server code |
| Data access | `@supabase/supabase-js` from client components | App has no server data layer; avoids API routes |
| Offline | None; online-only with clear error/offline states | User explicitly dropped IndexedDB entirely |
| Fetching | TanStack Query | Replaces live queries, gives retry, focus/reconnect refetch, invalidation |
| Schema | Normalized `category_id` foreign keys | Fresh start; avoids the name-as-join-key quirk |
| Categories in UI | Transactions still expose a derived `category` name | Keeps lists, filters, and spending code stable |
| Existing data | Fresh database, no migration | No active users |

## Architecture

```
Client components
  └─ TanStack Query hooks (useTransactions, useBudget, ...)
       └─ lib/db/repository.ts
            └─ @supabase/supabase-js (publishable key, user session)
                 └─ Supabase Postgres (RLS per user)
```

- No Dexie, `dexie-react-hooks`, or `uuid` dependency.
- No Next.js route handlers, server actions, or server-rendered user data.
- No API routes means no service-role key anywhere in the app.

## Auth

- New `AuthProvider` subscribes to `supabase.auth.onAuthStateChange` and exposes the session.
- `AuthGate` wraps the app shell in the root layout:
  - loading → skeleton/spinner,
  - no session → `AuthScreen`,
  - session → the existing app.
- `AuthScreen` has Sign in / Create account tabs (email + password), inline error messages, and a loading state.
- Sign-up behavior depends on the project's email-confirmation setting:
  - session returned → enter the app,
  - no session → show "Check your email to confirm your account".
- Settings shows the signed-in email and a Sign out action.
- Queries are disabled until a session exists.

## Database schema

All tables live in `public`, use UUID primary keys generated by Postgres, and carry `user_id`.

```sql
create table public.categories (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users (id) on delete cascade,
  name text not null check (length(btrim(name)) > 0),
  type text not null check (type in ('income', 'expense')),
  icon text,
  color text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (id, user_id)
);

create unique index categories_user_type_name_key
  on public.categories (user_id, type, lower(name));

create table public.transactions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users (id) on delete cascade,
  type text not null check (type in ('income', 'expense')),
  amount numeric(14, 2) not null check (amount > 0),
  category_id uuid not null,
  description text,
  date date not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  foreign key (category_id, user_id)
    references public.categories (id, user_id) on delete restrict
);

create table public.budgets (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users (id) on delete cascade,
  category_id uuid not null,
  amount numeric(14, 2) not null check (amount > 0),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (user_id, category_id),
  foreign key (category_id, user_id)
    references public.categories (id, user_id) on delete cascade
);
```

Indexes:

```sql
create index transactions_user_date_idx
  on public.transactions (user_id, date desc);
create index transactions_user_category_idx
  on public.transactions (user_id, category_id);
```

The `(user_id, category_id)` unique constraint on `budgets` and the `(user_id, type, lower(name))` unique index on `categories` already provide their leading-column indexes.

`updated_at` is maintained by one shared `set_updated_at()` trigger function and a `before update` trigger on each table:

```sql
create function public.set_updated_at()
returns trigger
language plpgsql
security invoker
set search_path = ''
as $$
begin
  new.updated_at = now();
  return new;
end;
$$;
```

### Delete behavior

- Deleting a category with transactions is rejected by the `ON DELETE RESTRICT` FK. The existing UI already requires reassignment first.
- Deleting a category cascades its budget row.
- Deleting an auth user cascades all three tables.

### Composite foreign keys

`(category_id, user_id) → categories (id, user_id)` guarantees a transaction or budget can never point at another user's category, even if an RLS policy is misconfigured.

## Row Level Security

Enable RLS on all three tables. Policies apply only to `authenticated`; `anon` has no access.

For each table, four policies:

```sql
-- SELECT
to authenticated
using ((select auth.uid()) = user_id);

-- INSERT
to authenticated
with check ((select auth.uid()) = user_id);

-- UPDATE (USING and WITH CHECK)
to authenticated
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id);

-- DELETE
to authenticated
using ((select auth.uid()) = user_id);
```

`auth.role()` is not used. `user_id` defaults to `auth.uid()`, so clients do not need to send it.

### Data API exposure

New public tables are no longer auto-exposed. The migration explicitly:

```sql
grant select, insert, update, delete
  on public.categories, public.transactions, public.budgets
  to authenticated;

revoke all
  on public.categories, public.transactions, public.budgets
  from anon;
```

The migration is delivered as `supabase/migrations/<timestamp>_init.sql` and run once in the Supabase SQL Editor.

## Type changes

`lib/db/schema.ts` (Dexie) is replaced by `lib/db/types.ts`:

```ts
export type TransactionType = "income" | "expense";

export interface Category {
  id: string;
  name: string;
  type: TransactionType;
  icon: string | null;
  color: string | null;
}

export interface Transaction {
  id: string;
  type: TransactionType;
  amount: number;
  categoryId: string;
  category: string; // derived display name from categories(name)
  description: string | null;
  date: string;
  createdAt: number;
}

export interface Budget {
  id: string;
  categoryId: string;
  amount: number;
  createdAt: number;
  updatedAt: number;
}
```

Removed: `CATEGORY_BUDGET_PREFIX`, `categoryBudgetId`, `parseCategoryBudgetId`, the Dexie `DB` class, and `newId()`.

## Repository (`lib/db/repository.ts`)

Public functions keep their current names so component edits stay small.

| Function | Supabase behavior |
| --- | --- |
| `listCategories` | `select` ordered by name |
| `addCategory` | insert `{ name, type }` |
| `updateCategory` | reject type change when transactions use the category; update row |
| `deleteCategory` | delete row (FK rejects if in use; budget cascades) |
| `transactionCountForCategory(categoryId)` | `count` transactions with that `category_id` |
| `reassignCategory(fromCategoryId, toCategoryId)` | update `category_id` on the source category's transactions |
| `addTransaction` | resolve category id from `(type, name)`, insert |
| `updateTransaction` | resolve category id, update by id |
| `deleteTransaction` | delete by id |
| `getCategoryBudgets` | select all budgets |
| `setCategoryBudget(categoryId, amount)` | validate, upsert on `(user_id, category_id)` |
| `deleteCategoryBudget(categoryId)` | delete by category id |
| `getMonthlySpent` | `date` range + `type = expense`, sum client-side |
| `getMonthlySpentByCategory` | same query, grouped by category name |
| `exportData` | select transactions with `categories(name)` |
| `importTransactions` | resolve/create categories, skip duplicate ids, chunked insert |

Notes:

- Category resolution is case-insensitive and scoped by type. Category-management functions take ids, so duplicate names across income/expense can never collide.
- Successful writes invalidate the shared TanStack Query cache; components do not each need mutation hooks.
- Errors are normalized into readable `Error` messages.
- `numeric` values are coerced with `Number(...)`.
- `timestamptz` values are mapped to epoch milliseconds for the existing `createdAt`/`updatedAt` number types; `date` stays a `YYYY-MM-DD` string.
- CSV rows with missing or non-UUID ids receive `crypto.randomUUID()`.
- Import is chunked (e.g. 500 rows per insert) to stay within request limits.

## Queries and hooks

- Shared singleton: `lib/query/client.ts`.
- Query keys:
  - `["categories"]`
  - `["transactions"]`
  - `["budgets"]`
  - `["monthly-spent"]`
  - `["monthly-spent-by-category"]`
- `useCategories(type?)`, `useTransactions()`, `useRecentTransactions(limit)` replace the live-query hooks.
- `useTotalBudget`, `useMonthlySpent`, `useCategoryBudgets`, `useMonthlySpentByCategory` keep their signatures and three-state semantics (`undefined` while loading).
- Writes invalidate all finance keys; the UI updates without a manual refresh.
- `refetchOnWindowFocus` and `refetchOnReconnect` are enabled.
- Hooks pass `enabled: !!session`.

## UI changes

- `BudgetView` and `DashboardView` use `budget.categoryId` instead of parsing `cat:<id>`.
- `TransactionForm` resolves its category budget by `categoryId`.
- `SettingsView` and `DeleteCategoryDialog` call the category-id-based count/reassign functions; the reassign select's value becomes the target category id.
- `TransactionsView`, `TransactionList`, `TransactionFilters`, `spending.ts`, and chart code keep using `transaction.category` (display name).
- `SettingsView` gains an Account card: signed-in email + Sign out.
- New shared components:
  - `OfflineBanner` — listens to `online`/`offline` events.
  - `DataError` — message + Retry button, shown when a query errors.
- PWA shell (manifest, service worker, update flow) is unchanged. Supabase API responses are not cached by the service worker.

## Rollout

1. Run the migration SQL in the Supabase SQL Editor.
2. Confirm all three tables show RLS enabled and four policies each.
3. Add `.env.local` locally; add both env vars to Vercel.
4. Deploy.
5. Bump the app version to `2.0.0`.
6. Create an account in the app and verify: add category → add transaction → set budget → export CSV → import CSV → sign out → sign in on a second browser.

Any existing finance data should be exported to CSV before deployment; it is not migrated automatically.

## Risks and trade-offs

- **No offline access.** Losing the connection means no finances until reconnect.
- **Email confirmation setting.** If confirmations are on, sign-up requires an email round trip before first sign-in.
- **RLS mistakes are silent.** A wrong policy shows zero rows rather than an error. The rollout checklist verifies row visibility per user.
- **Client-side aggregation.** Monthly totals are computed in the browser. This is fine for personal data volumes; move to a SQL view/RPC if data grows.
- **Breaking release.** Old IndexedDB data is ignored and the legacy database is deleted on boot.
